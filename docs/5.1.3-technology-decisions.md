# Technology decisions

The technologies Dark Portal is built with, each with the line of reason that
chose it. The arguments are in the issues named.

> **Draft for #7's design.**

| Area | Choice | Why |
| --- | --- | --- |
| language | Rust for `dp`, the collector and transform, built for `aarch64` and `x86_64` | one small binary with typed errors, the same language as Tile Lite Elite (#4) |
| logic | DuckDB SQL: views, macros and migrations, shipped in the image | transform once, read by every client alike (#4) |
| DuckDB in Rust | embedded, through the `duckdb` crate; its extensions installed into the image at build | each hour commits as one transaction, errors come back typed, and nothing downloads at run time |
| bronze | plain Parquet, one file per snapshot, written by `dp`, holding the listing columns and no raw JSON | readable by anything, and survives the loss of the catalog (#5); an unknown field is logged within the hour, and a year fits the bucket's free 20 GB |
| silver, gold, reference | DuckLake tables over Parquet, with a SQLite catalog | an hour commits or rolls back as one, and past states can be queried (#5) |
| HTTP | the `reqwest` crate, with `rustls` | no system OpenSSL to match on the host |
| JSON | `serde_json`, parsing the snapshot as a stream | a snapshot is about 28 MB; it is never held whole |
| scheduling | a systemd timer per job, and a VM-wide lock file | the host's own scheduler; the lock keeps jobs from overlapping (#11) |
| packaging | one container image per release, configured by its environment's `.env` | the same image in every environment (#11) |
| clients | a Python notebook on the owner's machine first, then a CLI command in `dp` | lookups and analysis are different jobs (#3) |
