# Configuration

Every setting Dark Portal has. A *keep* deletes what is older than it, by the
hour or day a row or file is for. Deployment settings are environment
variables in each environment's `.env`; product settings are constants in one
code module per area
([1.10](https://github.com/delphside/programme/blob/main/docs/1.10-development-standards.md#where-an-applications-settings-are-held)).

> **Draft for #7's design.** Measured sources are in the capacity plan
> [`DP_CP_2026_10`](https://github.com/delphside/programme/blob/main/applications/dark-portal/3.2.3-capacity-plan/DP_CP_2026_10.md);
> the rest are reviewed once collection runs.

## Deployment settings

| Variable | Holds |
| --- | --- |
| `DP_ENV` | the environment's name, from the list in #11 |
| `DP_DATA_DIR` | the environment's data folder, `/srv/dp/<env>` (#11) |
| `DP_BLIZZARD_CLIENT_ID` | the Blizzard client's ID |
| `DP_BLIZZARD_CLIENT_SECRET_FILE` | a file holding the client's secret, readable by the environment's user only; the secret is never logged, nor written to bronze or the export |
| `DP_BUCKET` | the Object Storage bucket bronze and the daily history are pushed to, or empty for none |
| `DP_BUCKET_ACCESS_FILE` | a file holding what gives `dp` write access to the bucket, readable by the environment's user only; required where `DP_BUCKET` is set, and read only then. Provisionally the address of a pre-authenticated request for the bucket ([5.1.3](5.1.3-technology-decisions.md)), which is a secret: never logged, nor written to bronze or the export |
| `DP_LOCK_FILE` | the VM-wide lock every writing job takes: `/srv/dp/dp.lock` |
| `DP_ADHOC_MEMORY_LIMIT` | DuckDB's `memory_limit` for an ad hoc query: 4 GB in production, 8 GB outside it |
| `DP_ADHOC_THREADS` | DuckDB's `threads` for an ad hoc query: 1 |
| `DP_CONTAINER_MEMORY` | the container's memory limit: the ad hoc limit plus 1 GB, so 5 GB in production and 9 GB outside it |

| HTTP timeout | 60 s for a snapshot, 10 s otherwise | collection | chosen |
| token margin | 1 hour | collection | chosen |
| item fetch rate | 50 a second | collection | half Blizzard's limit |
| item attempts | 3 in a run | collection | chosen: a blip pauses the whole fetch, so an item failing three turns likely has a fault of its own |
| lock wait | 10 min | scheduling | chosen |
| daily retry interval | 15 min | scheduling | chosen |
| daily retries end | 03:00 UTC | scheduling | chosen |
| daily timer start | 00:50 UTC | scheduling | between hourly runs |
| hourly and daily job DuckDB `memory_limit` | 1 GB | transform | `DP_CP_2026_10` |
| hourly and daily job DuckDB `threads` | 1 | transform | #12's agreed sizing |
| hourly processing bound | 5 min for `transform` and `export` of one hour together; a run over it is logged as a warning; a run's own work is shared across the hours it processed; `dp transform` or `dp export` run alone counts its own time against the same bound | transform | chosen: #5's estimate of 5 to 10 s, inside #11's deploy window of :40 to :10 |
| default *N* window | 7 days | profiles | chosen |
| turnover window | 24 hours | profiles | chosen |
| depth ladder cut-off | 48 hours of depth | profiles | chosen: the longest duration |
| hourly keep | 4 weeks | storage | R2 |
| daily keep | indefinitely | storage | R2 |
| silver keep | indefinitely, until #5 sets one | storage | #5 |
| bronze keep on the host | 7 days, for snapshot files; item files are kept | storage | chosen, within #5's few days |
| bronze keep in the bucket | 1 year, by the bucket's lifecycle rule on `bronze/` | storage | #5 |
| daily history in the bucket ([5.4.2](5.4.2-storage-schema.md#the-bucket)) | indefinitely | storage | R2 |
| bucket push timeout | 5 min for one object, upload included | storage | chosen: well over what an hour's bronze file needs at the host's upload speed; reviewed when the first pushes are timed |
