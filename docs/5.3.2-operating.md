# Operating

The owner's manual steps for running `dp` on a host: installing the units,
the `.env`, the secret files, and the bucket's access. What the units run is
[5.1.3](5.1.3-technology-decisions.md); each setting is in
[5.4.1](5.4.1-configuration.md).

> **Draft for #7's design.** The environments, the registry and the release's
> deploy are #11's: where a step needs one, it names the placeholder #11 fills.
> Nothing here names a tenancy, a host or an address; the repository is public.

## What a host holds

| Path | Holds |
| --- | --- |
| `/usr/local/libexec/dp/dp-run` | [`deploy/dp-run`](../deploy/dp-run), which runs one job in the image |
| `/etc/systemd/system/dp-{hourly,daily}@.{service,timer}` | the units in [`deploy/systemd/`](../deploy/systemd), one instance per environment, named for it (`dp-hourly@<env>.timer`) |
| `/etc/dp/<env>.env` | the environment's `.env`: every deployment setting of [5.4.1](5.4.1-configuration.md), and `DP_IMAGE`, the release's image |
| `/etc/dp/secrets/<env>/` | the environment's secret files, readable by its user only |
| `/srv/dp/<env>`, `/srv/dp/dp.lock` | the environment's data folder and the VM-wide lock (`DP_DATA_DIR` and `DP_LOCK_FILE`, [5.4.1](5.4.1-configuration.md#deployment-settings)) |

## Install the units

1. Install the script and the four unit files:

   ```bash
   install -m 0755 -D deploy/dp-run /usr/local/libexec/dp/dp-run
   install -m 0644 deploy/systemd/dp-*@.{service,timer} /etc/systemd/system/
   ```

2. Make the environment's user and its folders: the data folder owned by the
   user, and the lock file made empty and writable by every environment's
   user. `dp-run` never makes the lock file: it stops with exit `2` where it is
   missing.
3. Write `/etc/dp/<env>.env` and the secret files, below.
4. Pull the release's image, then `systemctl daemon-reload` and
   `systemctl enable --now dp-hourly@<env>.timer dp-daily@<env>.timer`.
5. Check `systemctl list-timers 'dp-*'` shows both timers with a next run, and
   start `dp-hourly@<env>.service` once by hand and read its journal.

## The `.env`

One `KEY=value` to a line, with no quotes and no `export`: systemd and Docker
read the file differently, and only the plain form means the same to both.

Beside the settings of [5.4.1](5.4.1-configuration.md), `dp-run` reads:

| Variable | Holds |
| --- | --- |
| `DP_IMAGE` | the image to run, name and tag, set by the release's deploy (#11) |
| `DP_RUN_USER` | the environment's user as `uid:gid`, which owns its data folder and secret files and which the container runs as |

## The secret files

`DP_BLIZZARD_CLIENT_SECRET_FILE` and `DP_BUCKET_ACCESS_FILE` each name a file
holding one value. Make each mode `0400`, owned by the environment's user, and
never put it in the `.env`, the repository or a log. `dp-run` mounts each
read-only at the same path.

## The bucket's access

`dp daily` writes to the bucket with an Object Storage *pre-authenticated
request* (PAR), whose URL is the secret in `DP_BUCKET_ACCESS_FILE`
([5.1.3](5.1.3-technology-decisions.md)). It stops working on its expiry date
and then `dp daily` ends its push on `BUCKET_ACCESS_REFUSED` and exits `3`,
after the day's close ([5.1.1](5.1.1-architecture.md#restarts-and-recovery)).

**Create it**, in the console under the bucket's *Pre-Authenticated Requests*:

1. Choose the *bucket* as the target, and *Permit object writes* as the
   access type: `dp` only puts objects.
2. Choose an expiry date, and record it where the owner keeps dates: the
   console shows it, and nothing in `dp` warns before it.
3. Copy the URL when it is shown, since it is shown once. It ends `/o/`.
4. Write it to the secret file, replacing the old value. `dp` takes it as it
   stands and appends each object's name.

**Renew it** before the expiry date: create a new one as above, replace the
secret file's contents, and run `dp daily` once by hand
(`systemctl start dp-daily@<env>.service`) to see a push succeed. Then delete
the old PAR in the console, which revokes it.

**If the URL leaks**, delete its PAR in the console at once and create a new
one.

## When a job fails

`journalctl -u dp-hourly@<env>` and `-u dp-daily@<env>` hold each run's log;
the exit status says what to do
([programme 1.10](https://github.com/delphside/programme/blob/main/docs/1.10-development-standards.md#what-a-scripts-exit-status-means)).
A unit that shows `failed` is a run that did not complete: `75` left an hour or
a day for a later run, and the next timer start repeats it. `dp daily` has
already retried itself on `75` until the daily retries end
([5.1.1](5.1.1-architecture.md#restarts-and-recovery)). A unit that shows
`failed` with a timeout was stopped at its run time limit
([5.4.1](5.4.1-configuration.md#product-settings)); the next timer start
repeats what it left.

**A run by hand while its unit's run is live** exits `75`, not `2`: `dp-run`
names the container for its job and environment (`dp-<job>-<env>`), and asks
`docker ps` for that name before it runs, since docker's own `125` for a name
in use cannot be told from its other failures. The run that is live goes on;
run it again once it ends. A stopped container that still holds the name is not
a live run, and `docker run` refuses it as exit `2`.

## What the timings are for

Every job's final line carries its total time, `total_seconds`, and each step's,
in seconds: for `dp hourly`, `collect_seconds`, `items_seconds`,
`transform_seconds` and `export_seconds`; for `dp daily`, `close_seconds`,
`export_seconds`, `push_seconds`, `expiry_seconds`, `temporary_seconds` (stale
temporary files and spill folders) and `items_retry_seconds`, and the number of
`attempts`; the single-step commands carry the total. A step that failed still reports
its time. A step that did not run reports none: under `dp hourly`, where the
lock is held past the lock wait, `items_seconds`, `transform_seconds` and
`export_seconds` are absent (`collect_seconds` and the total are there), never
null or `0`; a `dp daily` that stops before its close, as one too late to close
or whose day cannot be closed, carries the total only. Dark Portal's monthly
capacity plan reads them against the hourly processing bound, the daily
deadline and the two run time limits
([5.4.1](5.4.1-configuration.md#product-settings)). A limit that sits near its
use is changed in its setting, by a person: nothing changes one on its own.

## `dp-run`'s exit statuses

`dp-run` exits with `dp`'s own statuses unchanged, and maps the rest
([programme 1.10](https://github.com/delphside/programme/blob/main/docs/1.10-development-standards.md#what-a-scripts-exit-status-means)):

| Case | Exit |
| --- | --- |
| no subcommand, an unknown option or an unknown subcommand | `64` |
| a setting `dp-run` needs is missing (a secret file's included), `DP_ENV_FILE` is not `<environment>.env`, or the lock file is missing | `2` |
| the docker daemon is unreachable, or a run of the same job is live | `75` |
| docker's own `125`, `126` or `127`: it could not run the container or its command | `2` |
| `dp` ended with `0`, `1`, `2`, `3`, `64`, `70` or `75` | the same status |
| anything else, such as a kill's `137` | `70` |
