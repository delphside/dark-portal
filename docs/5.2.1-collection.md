# Collection

How `dp collect` fetches each hour's EU commodities snapshot, and `dp items`
the item data, into bronze. The snapshot is parsed into Parquet columns; each
item response is kept as Blizzard sent it. What follows from bronze is in
[5.2.2](5.2.2-listing-lifecycle-and-events.md); the run as a whole is in
[5.1.1](5.1.1-architecture.md#the-hourly-run). Every value named here is in
[5.4.1](5.4.1-configuration.md).

> **Draft for #7's design.**

## The snapshot

`dp collect` collects the snapshot for the *current hour*, fixed when it
starts: the [hour starting](5.2.2-listing-lifecycle-and-events.md#times) in
which it runs, or the hour before where it starts within that hour's retry
window. So a run a reboot delayed until 11:10 still takes hour 10:00, which
Blizzard serves until about 11:31.

1. If bronze holds a file for the current hour, exit `0`: the hour is
   collected.
2. Take an access token by the OAuth client-credentials grant from
   `https://oauth.battle.net/token`, or reuse the cached one while it has more
   than the token margin left. A token lasts 24 hours.
3. `GET https://eu.api.blizzard.com/data/wow/auctions/commodities?namespace=dynamic-eu`.
4. Read the `last-modified` header. If its hour starting is:
   - before the current hour, Blizzard has not refreshed yet: wait the poll
     interval and go back to step 3;
   - the hour after the current one, Blizzard has moved on: the current hour
     is a gap, exit `75`;
   - later still, the host's clock is wrong: exit `2`.
5. Parse the body as a stream into the listing columns and write the hour's
   file under a temporary name. Then take the VM-wide lock and rename the file
   into place, so a reader sees only whole files.

Blizzard refreshes the snapshot at about :31:40 past each hour. Steps 3 and 4
repeat until the retry window closes; the hour is then a gap, which
`dp transform` records when it finds the file missing.

**A rerun in a collected hour does nothing**, so the timer, a person and a
retry can all start it safely.

## Item data

After the snapshot, `dp items` fetches every item ID in bronze's snapshot
files that bronze's item files have no response for, from
`https://eu.api.blizzard.com/data/wow/item/{id}?namespace=static-eu&locale=en_GB`,
at the item fetch rate, and writes the responses as one file, where it fetched
any. A 404 is written too, with its status and no body, so only `dp daily`
asks again, for each item whose latest response is a 404. The first run
fetches every commodity in the snapshot
([5.2.3](5.2.3-consumable-profiles.md#which-items)); later runs fetch only
items new to the house. An item with no response yet is fetched on the next
run, and its profile shows its ID until it has one.

**The item fetch ends the lock wait before the next hourly timer start**, so
it and its write never run into the next hour's run: no request starts unless
its HTTP timeout ends before then, and the items not reached wait for the
next run. A failure that is Blizzard's state rather than the item's (a
timeout, no answer, 429, 502, 503 or 504) pauses the whole fetch for the
backoff or the `Retry-After`, and puts the item at the back of the queue; an
item is asked at most three times in a run.

## What bronze holds

The two folders and their columns are in
[5.4.2](5.4.2-storage-schema.md#bronze-parquet-files). The snapshot's columns
are Blizzard's own values, `time_left` as given. An item response is kept
whole as received, whatever its fields, so a change to it needs nothing here; a
body that is not a JSON object is not kept ([item data](#item-data)).

## When Blizzard's response changes

`dp` tolerates a change to Blizzard's snapshot format or timing where the
data stays sound, and records each as a *warning* in the run's report and log
([1.10's error scheme](https://github.com/delphside/programme/blob/main/docs/1.10-development-standards.md#errors-one-scheme-for-every-system)):
the exit stays `0` unless something else fails, so a person, or the alerting of
[#2](https://github.com/delphside/dark-portal/issues/2), sees the change in the
first hour it appears. A change that would leave an hour partial is not
tolerated, since a partial hour reads the listings it lacks as sales: the hour
is a gap, with a fatal code of its own.

The warnings of a run are each logged where they are raised. The report's
`warnings` lists every warning raised with its own metadata, in the order
raised; its `warnings` metadata names their codes, each once, in the order first
raised. `dp hourly`'s report lists those of its
steps. Where the run also fails, the outcome and the exit are the failure's, and
the warnings are still listed. Each run reports what it sees, so a change that
lasts repeats its warning every hour: raising them is the whole of `dp`'s part,
and deduplicating is the alerting's, in
[#2](https://github.com/delphside/dark-portal/issues/2).

| What Blizzard changed | What `dp` does | Code and its metadata |
| --- | --- | --- |
| a field in a listing or its `item` object, or at the body's top level beside `auctions` (`_links` is known), that the parser does not know | the field is ignored, whatever it holds, and the hour is collected | warning `SNAPSHOT_FIELD_NEW`: `hour`, `fields`, each name once, an `item` field as `item.<name>`, a top-level one as `$.<name>` |
| a `time_left` that is not one of the four bands, an empty one included | bronze keeps the value as given and the transform processes the hour ([5.2.2](5.2.2-listing-lifecycle-and-events.md#a-time-left-that-is-not-a-band)) | warning `TIME_LEFT_UNKNOWN`, from `dp transform`, one for each hour: `hour`, `values`, the distinct values in sorted order, and `listings`, the count of listings holding one |
| a field the parser needs (`id`, `item` and its `id`, `quantity`, `unit_price`, `time_left`) is missing | the hour is not collected: a gap | fatal `SNAPSHOT_SHAPE_CHANGED`, *unexpected*, exit `70`: `field`, the path that failed, and `listings`, those read before it |
| such a field is of another kind: text, a boolean, null, an array or an object where a number is needed, or a non-text `time_left` | as above | as above |
| the structure changed: `item` an array or a text, `item.id` moved, `auctions` missing, renamed or not a sequence, a listing that is not an object | as above | as above, the field `item`, `item.id`, `auctions`, `auctions[]` or `$` (the body, where it is valid JSON that is not an object) |
| a number the column cannot hold: negative (`-0` is negative), a decimal (a number written with a fraction or an exponent, `2.0` and `1e3` included), or above the column's range (`quantity` above 4,294,967,295 for example) | the hour is not collected: a gap | fatal `SNAPSHOT_VALUE_UNEXPECTED`, *unexpected*, exit `70`: `field`, `value` (cut at 5.4.1's [longest quoted value](5.4.1-configuration.md#product-settings)) and `listings` |
| a `quantity` or a `unit_price` of 0 | as above | as above |
| text that `dp` keeps, `time_left`, beyond the longest text ([5.4.1](5.4.1-configuration.md#product-settings)), counted in bytes | as above | as above |
| the snapshot is refreshed at a time past the hour outside the expected refresh window | the hour is collected | warning `REFRESH_TIME_MOVED`: `hour`, `refresh_past_hour`, `window_start`, `window_end` |
| the time between one held hour's `last-modified` and that of the held hour before it, the two hours held one after the other with none missed between, is outside the expected refresh interval | the hour is processed | warning `REFRESH_INTERVAL_CHANGED`, from `dp transform`: `hour`, `last_modified`, `previous_last_modified`, `interval_seconds` |
| an hour is missed | `dp transform` records it in `meta.gap` ([5.2.2](5.2.2-listing-lifecycle-and-events.md#a-missed-hour)) | warning `HOUR_MISSED`, from `dp transform`, one for each hour missed: `hour` |
| the snapshot is refreshed more often than hourly | `dp probe`, once a day, sees a snapshot newer than the hour before's by less than the least about an hour | warning `REFRESH_MORE_OFTEN`: `hour`, the hour before, whose file it compared, `collected_last_modified`, `latest_last_modified` |
| `dp probe` cannot read the hour before's bronze file, take a token or ask Blizzard | nothing: it never fails | warning `PROBE_FAILED`: `cause`, `cause_message` |
| the hour before's bronze file is not there | nothing to compare: the probe asks Blizzard nothing | none |
| an item response lacks a path the reference table reads (`name`, `item_class.name`, `item_subclass.name`, `sell_price`, `purchase_price`) or has it of another type | the item is kept, that reference field is null (`sell_price` 0, as before) | warning `ITEM_FIELD_MISSING`, from `dp transform`, one for each path, for the answers new since the table was last built: `path`, `items`, a count, and `first_items`, the 5 lowest item IDs ([5.4.1](5.4.1-configuration.md#product-settings)'s *item IDs named*) |

**Which listings can be kept.** A listing is kept only where its value cannot
bias the sales inference ([5.2.2](5.2.2-listing-lifecycle-and-events.md)): a
wrong ID, item, quantity or price changes what a disappearance is read as, so
the hour is a gap. A `time_left` that is not a band, an empty one included, is
the one value kept, since only EV-5 reads it and an unknown one is read as the
more careful *cancelled*. Its length is bounded all the same, so a body of
garbage is not stored; the bound applies to text `dp` keeps, not to the value
of a field it does not know and does not read.

**What a number is.** A JSON number written with a fraction or an exponent
(`2.0`, `1e3`) is a decimal, and `-0` is negative, so each is
`SNAPSHOT_VALUE_UNEXPECTED`. An `id` or an `item.id` of 0 is kept; `quantity`
and `unit_price` must be at least 1. A value is quoted as `dp` reads it: text
whole, a number beyond 64 bits as its double, each cut at the longest quoted
value.

**What a body is.** A body that is not JSON, or is cut off, is
`SNAPSHOT_BODY_UNUSABLE`. A body that is valid JSON but not an object is
`SNAPSHOT_SHAPE_CHANGED` at `$`.

**Enumerated fields and booleans.** `time_left` is the only enumerated field
of a snapshot listing, and there is no boolean in one. The reference table
reads text and numbers from an item response and no enumerated field or
boolean (`vendor_sells` is the owner's, null until set). Were one read, the same
rule applies: the value is kept as given, a missing one or one of another type
is `ITEM_FIELD_MISSING`, and the item never fails.

**Item responses** that are JSON objects are kept whole as received, so a change
to their fields costs nothing in bronze; only the reference extraction reads
them. A body that is not JSON, or is JSON but not an object, is a body that
cannot be read: the item is fetched again on the next run.

**The refresh time** is the time past the hour of the served `last-modified`,
which every bronze row holds as `last_modified`: its history needs nothing
beyond bronze. `dp collect` puts it on its report as `refresh_past_hour`, as
`mm:ss`, when it read a snapshot: a run that read none (a collected hour rerun,
or a failure before the snapshot) carries none. The *expected refresh window* and the *expected refresh interval* are
product settings ([5.4.1](5.4.1-configuration.md#product-settings)), their
ends included: the window ends at :45:00, so :45:00 is inside and :45:01 outside.

**A refresh that changes** shows as these warnings together:
- *daily* refreshes: `HOUR_MISSED` for each hour between, and no
  `REFRESH_INTERVAL_CHANGED`, which is judged only between consecutive held
  hours;
- *half-hourly*: `dp collect` takes one snapshot an hour and needs no change,
  and meets the :31 refresh whatever the other does, so only `dp probe` sees it.

`HOUR_MISSED` is the one place a gap is a warning. The run that missed the hour
already ended with its own error (`RETRY_WINDOW_CLOSED`, `HOUR_IS_A_GAP`), and
`dp transform` raises the warning once the hour is recorded.

### The refresh probe

`dp probe` runs once a day, at 12:05 UTC, a minute well away from the hourly
run's :35. It reads the `last-modified` of bronze's snapshot of the hour before,
takes a token of its own and asks Blizzard for the snapshot with
`If-Modified-Since` that time. Blizzard answers `304` where nothing is newer;
an answer of `200` is read for its `last-modified` header and its body is
dropped unread, so a server that ignores the condition costs a connection and
not a download, and the probe compares the header itself. A `200` without a
`last-modified` is `PROBE_FAILED`. Its two requests take the other HTTP timeout,
10 s, and it never retries. A `last-modified`
later than the one collected, by less than the least about an hour (the
expected refresh interval's start), is `REFRESH_MORE_OFTEN`: a refresh that has
only moved to a few minutes past the hour is newer by about an hour, and is no
warning. On the day an hourly refresh moves to just after the hour, the probe
raises one `REFRESH_MORE_OFTEN` beside the true `REFRESH_TIME_MOVED`, which
one sample a day cannot avoid; it clears the next day.

It never writes bronze, takes no lock and so waits for none, and caches no
token, so it cannot race the hourly run for any of them. It never fails a run:
whatever it meets is `PROBE_FAILED`, and exit `0`. Where the hour before's
file is not there, nothing is compared and it asks Blizzard nothing; where it
is there and cannot be read, that is `PROBE_FAILED`.

Its timer is not persistent, so a host down at 12:05 gets no catch-up run, and
its unit has `Restart=no`. Its final line carries `total_seconds`, as every
job's does.

It is a command of its own, `dp-probe@.timer`, since `dp daily` starts at 00:50
between hourly runs and its limits are built around that.

## Limits

Blizzard allows a client 36,000 requests an hour and 100 a second. An hour
takes one snapshot request and its polls, a token request about once a day,
and any new items.

## When it fails

Errors follow the programme's
[error scheme](https://github.com/delphside/programme/blob/main/docs/1.10-development-standards.md#errors-one-scheme-for-every-system).
The snapshot comes before the pivot, so its errors end `dp collect` with the
exits in this table.

| What happens to the snapshot | Type | Exit |
| --- | --- | --- |
| Blizzard times out, cannot be reached, or answers 429, 502, 503 or 504 | technical, blip: retried with backoff, or after its `Retry-After`, until the retry window closes | `75` once it closes |
| a request with a cached token is refused (401) | technical, blip: a new token is taken once | `2`, if the new token is refused too |
| a new token is refused (401) | technical, fundamental: the client secret is wrong | `2` |
| Blizzard answers 403 or 404, or a `last-modified` whose hour is two or more after the current one | technical, fundamental | `2` |
| the `last-modified` is in the hour after the current one | technical, blip: Blizzard has moved on; the hour is a gap | `75` |
| the `last-modified` is still before the current hour when the retry window closes | technical, blip: polled every poll interval until then; the hour is a gap | `75` |
| the lock is held past the lock wait | technical, blip | `75` |
| Blizzard answers 400, 500 or another status, a body the parser cannot use (`SNAPSHOT_BODY_UNUSABLE`) or no `last-modified` | unexpected | `70` |
| a listing lacks a field the parser needs (`SNAPSHOT_SHAPE_CHANGED`), the hour being a gap | unexpected | `70` |
| a needed field is of another kind: text, a boolean, null, an array or an object where a number is needed (`SNAPSHOT_SHAPE_CHANGED`) | unexpected | `70` |
| the structure changed: `item` not an object, `item.id` moved, `auctions` missing, renamed or not a sequence, a listing not an object (`SNAPSHOT_SHAPE_CHANGED`, with the path) | unexpected | `70` |
| a number the column cannot hold: negative, a decimal, out of range (`SNAPSHOT_VALUE_UNEXPECTED`) | unexpected | `70` |
| a `quantity` or `unit_price` of 0 (`SNAPSHOT_VALUE_UNEXPECTED`) | unexpected | `70` |
| text beyond the longest text (`SNAPSHOT_VALUE_UNEXPECTED`) | unexpected | `70` |
| DuckDB cannot write the bronze file (`BRONZE_WRITE_FAILED`), out of memory included | unexpected | `70` |
| the disk is full | technical, fundamental | `2` |
| another file in the data folder cannot be read or written, such as one whose owner or mode is wrong (`LOCAL_IO_FAILED`) | technical, fundamental | `2` |

The item fetch, the transform and the export come after the pivot. An error in
one is logged with its type under the error scheme, an item lookup's typed as
in the snapshot's table, and an item's 404 is data, not an error. Run alone, a
step exits:

- `dp transform` and `dp export`, for a fatal error, by its type, as the error
  scheme sets out, such as:
  - `75` where the lock is held past the lock wait;
  - `2` for `LAKE_UNAVAILABLE`, a full disk or out of memory;
  - `70` for `LAKE_FAILED`;
- `dp export`, for an error it carried on past, `3`;
- `dp items`, as the paragraph on its own pivot says.

Under `dp hourly` a failed step gives that step exit `3`, as the list of
`dp hourly`'s exits says.

`dp items` run alone has a pivot of its own, its first request. A failure
before it stops the run with that error's exit: DuckDB failing to read bronze
(`BRONZE_READ_FAILED`) and DuckDB failing to open its store for the responses
(`BRONZE_WRITE_FAILED`) are unexpected, exit `70`. After it each item is a unit
of work the run carries on past, and every failure is a carried error with exit
`3`.

| What happens after the pivot | Then |
| --- | --- |
| an item lookup times out, cannot be reached, or answers 429, 502, 503 or 504 | the fetch pauses for the backoff or the `Retry-After`, and the item is asked again later in the run; after its third attempt, or when the item fetch ends, it is fetched on the next run |
| an item lookup answers 401 | a new token is taken once and the item asked again; if the new token is refused too, the client secret is wrong (technical, fundamental) and the item is fetched on the next run |
| an item lookup answers 404 | Blizzard has no data for it yet: it is recorded and logged as a warning, and asked again by `dp daily` |
| a body is a JSON object that lacks a path the reference table reads, or has it of another type, a decimal or negative price included (`ITEM_FIELD_MISSING`) | the item is kept and that reference field is null: a warning, exit `0` |
| an item lookup answers 400, 403, 500 or another status, or a body that cannot be read: not JSON, or JSON that is not an object | the item is fetched on the next run; a JSON object is kept whole whatever its fields |
| the transform fails | the next run reprocesses the hour |
| a snapshot has a `time_left` that is not a band (`TIME_LEFT_UNKNOWN`), a refresh outside the window (`REFRESH_TIME_MOVED`, from `dp collect`), a time between two hours' `last-modified` that is not about an hour (`REFRESH_INTERVAL_CHANGED`), or an hour missed (`HOUR_MISSED`) | warnings: the hour is processed, exit `0`. A rebuild of the lake raises the hour warnings again for every hour it processes; `ITEM_FIELD_MISSING` follows its own rule of new answers |
| a bronze file is unreadable (`BRONZE_HOUR_UNREADABLE`), or holds a repeated ID, a null or another hour (`BRONZE_HOUR_INVALID`) | unexpected: the transform stops at that hour, keeping the hours before it, and run alone exits `70`; every run stops there until the file is repaired |
| DuckDB cannot write the item responses to bronze (`BRONZE_WRITE_FAILED`) | unexpected: a carried error, exit `3`, and the items not written are fetched on the next run |
| the export fails | the next run writes every hour the export lacks |
| DuckDB runs out of memory in `dp transform` (`OUT_OF_MEMORY`) | technical, fundamental: the transform stops, and run alone exits `2` |
| DuckDB runs out of memory in `dp export` (`OUT_OF_MEMORY`) | technical, fundamental. Opening or migrating the lake stops the export, and run alone it exits `2`. Reading the committed hours, rewriting `item_day` or `item`, or writing an hour is an error, and stops the export: no later file is written. Reading and rewriting are errors for no hour, writing an error for that hour. Run alone it exits `3` |

`dp hourly` runs every step, and exits with:

- `collect`'s exit, where that is not `0`;
- otherwise `3`, where a later step failed, whatever the failure's type; the
  step's own error, with its type, is in the log;
- otherwise `0`.

The steps that failed are the run's errors, each logged with its type. Where
the lock is held past the lock wait the later steps do not run: the exit is
`collect`'s where that is not `0`, otherwise `75`.
