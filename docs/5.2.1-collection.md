# Collection

How `dp collect` fetches each hour's EU commodities snapshot and Blizzard's
item data, and lands them in bronze unchanged. What follows from bronze is in
[5.2.2](5.2.2-listing-lifecycle-and-events.md); the run as a whole is in
[5.1.1](5.1.1-architecture.md#the-hourly-run).

> **Draft for #7's design.**

## The snapshot

1. Take an access token by the OAuth client-credentials grant from
   `https://oauth.battle.net/token`, or reuse the cached one while it has more
   than an hour left. A token lasts 24 hours.
2. `GET https://eu.api.blizzard.com/data/wow/auctions/commodities?namespace=dynamic-eu`.
3. Read the `last-modified` header. Its hour starting is the snapshot's hour
   ([5.2.2](5.2.2-listing-lifecycle-and-events.md#times)).
4. If that hour already has a bronze file, the snapshot has not refreshed yet:
   wait and go back to step 2.
5. Parse the body as a stream into the listing columns, and write the hour's
   file to a temporary name, then rename it into place, so a reader never sees
   half a file.

The snapshot refreshes at about :31:40 past each hour, so the timer starts the
run at :35. It retries steps 2 to 4 until :25 past the next hour, then stops
with the hour recorded as a gap, since the next run's snapshot replaces it.

**Each hour is fetched at most once.** Step 4 makes a rerun in the same hour
do nothing, so the timer, a person and a retry can all start it safely.

## Item data

After each snapshot is written, every item id it holds that bronze has no item
record for is fetched from
`https://eu.api.blizzard.com/data/wow/item/{id}?namespace=static-eu&locale=en_GB`
and written raw to bronze's item folder. The first run fetches about 11,700;
later runs fetch only new items, usually none. An item that fails is retried
on the next run, and its profile shows its id until then.

## Bronze

| Folder | One file per | Columns |
| --- | --- | --- |
| `bronze/commodities/eu/` | snapshot hour, `YYYY-MM-DDTHH.parquet` | the snapshot's hour, `last-modified` and fetch time; each listing's id, item, quantity, unit price and time-left band |
| `bronze/items/` | fetch run | the item id, the fetch time and the response body as JSON |

The columns are defined in [5.4.5](5.4.5-data-dictionary.md). A listing field
the parser does not know is logged as a warning naming it, so a change to
Blizzard's format is seen in the first hour it appears.

## Limits

Blizzard allows a client 36,000 requests an hour and 100 a second. An hour
takes two requests, a token and a snapshot, plus any new items. The first
run's item fetch is paced at 50 a second, about 4 minutes.

## When it fails

Errors follow the programme's error scheme
([1.10](../programme/docs/1.10-development-standards.md#errors-one-scheme-for-every-system)).

| What happens | Type | Exit |
| --- | --- | --- |
| Blizzard times out, or answers 429 or 5xx | technical, blip: retried with backoff until :25 | `75` once the window closes |
| the token is refused (401) | technical, fundamental: the client secret is wrong | `2` |
| the body does not parse | technical, fundamental | `2` |
| the disk is full | technical, fundamental | `2` |
| an item lookup fails | technical, blip: logged, retried next run | `3` |
