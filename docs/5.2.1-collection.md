# Collection

How `dp collect` fetches each hour's EU commodities snapshot, and `dp items`
the item data, into bronze. The snapshot is parsed into Parquet columns; each
item response is kept as Blizzard sent it. What follows from bronze is in
[5.2.2](5.2.2-listing-lifecycle-and-events.md); the run as a whole is in
[5.1.1](5.1.1-architecture.md#the-hourly-run). Every value named here is in
[5.4.1](5.4.1-configuration.md).

> **Draft for #7's design.**

## The snapshot

`dp collect` collects the snapshot for the *current hour*, fixed when it
starts: the [hour starting](5.2.2-listing-lifecycle-and-events.md#times) in
which it runs, or the hour before where it starts within that hour's retry
window. So a run a reboot delayed until 11:10 still takes hour 10:00, which
Blizzard serves until about 11:31.

1. If bronze holds a file for the current hour, exit `0`: the hour is
   collected.
2. Take an access token by the OAuth client-credentials grant from
   `https://oauth.battle.net/token`, or reuse the cached one while it has more
   than the token margin left. A token lasts 24 hours.
3. `GET https://eu.api.blizzard.com/data/wow/auctions/commodities?namespace=dynamic-eu`.
4. Read the `last-modified` header. If its hour starting is before the current
   hour, Blizzard has not refreshed yet: wait the poll interval and go back to
   step 3. If it is after the current hour, the host's clock is wrong: exit
   `2`.
5. Take the VM-wide lock, parse the body as a stream into the listing
   columns, write the hour's file under a temporary name, and rename it into
   place, so a reader sees only whole files.

Blizzard refreshes the snapshot at about :31:40 past each hour. Steps 3 and 4
repeat until the retry window closes; the hour is then a gap, which
`dp transform` records when it finds the file missing.

**A rerun in a collected hour does nothing**, so the timer, a person and a
retry can all start it safely.

## Item data

After the snapshot, `dp items` fetches every item ID in bronze's snapshot
files that bronze's item files have no response for, from
`https://eu.api.blizzard.com/data/wow/item/{id}?namespace=static-eu&locale=en_GB`,
at the item fetch rate, and writes the responses as one file, where it fetched
any. A 404 is written too, with its status and no body, so only `dp daily`
asks again, for each item whose latest response is a 404. The first run
fetches every commodity in the snapshot
([5.2.3](5.2.3-consumable-profiles.md#which-items)); later runs fetch only
items new to the house. An item with no response yet is fetched on the next
run, and its profile shows its ID until it has one.

## What bronze holds

The two folders and their columns are in
[5.4.2](5.4.2-storage-schema.md#bronze-parquet-files). A listing field the
parser does not know is logged as a warning naming it, so a change to
Blizzard's format is seen in the first hour it appears.

## Limits

Blizzard allows a client 36,000 requests an hour and 100 a second. An hour
takes one snapshot request and its polls, a token request about once a day,
and any new items.

## When it fails

Errors follow the programme's
[error scheme](https://github.com/delphside/programme/blob/main/docs/1.10-development-standards.md#errors-one-scheme-for-every-system).
The snapshot comes before the pivot, so its errors end `dp collect` with the
exits below.

| What happens to the snapshot | Type | Exit |
| --- | --- | --- |
| Blizzard times out, or answers 429, 502, 503 or 504 | technical, blip: retried with backoff, or after its `Retry-After`, until the retry window closes | `75` once it closes |
| a request with a cached token is refused (401) | technical, blip: a new token is taken once | as below, if the new token is refused too |
| a new token is refused (401) | technical, fundamental: the client secret is wrong | `2` |
| Blizzard answers 403 or 404, or a `last-modified` after the current hour | technical, fundamental | `2` |
| the `last-modified` is still before the current hour when the retry window closes | technical, blip: polled every poll interval until then; the hour is a gap | `75` |
| the lock is held past the lock wait | technical, blip | `75` |
| Blizzard answers 400, 500 or another status, a body the parser cannot use or no `last-modified` | unexpected | `70` |
| the disk is full | technical, fundamental | `2` |

The item fetch, the transform and the export come after the pivot, so each
error is logged with its type under the error scheme, an item lookup's as in
the snapshot's table, and gives the step exit `3`:

| What happens after the pivot | Then |
| --- | --- |
| an item lookup times out, or answers 429, 502, 503 or 504 | retried with backoff, or after its `Retry-After`, as for the snapshot; if it still fails when the item fetch ends, the item is fetched on the next run |
| an item lookup answers 401 | a new token is taken once and the item asked again; if the new token is refused too, the client secret is wrong (technical, fundamental) and the item is fetched on the next run |
| an item lookup answers 404 | Blizzard has no data for it yet (technical, fundamental): it is recorded, and asked again by `dp daily` |
| an item lookup answers 400, 403, 500 or another status, or a body that cannot be read | the item is fetched on the next run |
| the transform fails | the next run reprocesses the hour |
| the export fails | the next run writes every hour the export lacks |

`dp hourly` runs every step, and exits with:

- `collect`'s exit, where that is not `0`;
- otherwise `3`, where a later step failed;
- otherwise `0`.
