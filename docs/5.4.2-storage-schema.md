# Storage schema

Every file and table Dark Portal keeps in its data folder, and their columns.
Each column's type and meaning is in [5.4.5](5.4.5-data-dictionary.md); the
layers are explained in [5.1.1](5.1.1-architecture.md#data-layers), and how
long each is kept in [5.4.1](5.4.1-configuration.md#product-settings).

> **Draft for #7's design.** Stage 1's files and tables only.

## Bronze: Parquet files

| File | One per | Columns |
| --- | --- | --- |
| `bronze/commodities/eu/YYYY-MM-DDTHH.parquet` | snapshot hour | `hour`, `last_modified`, `fetched_at`, `id`, `item`, `quantity`, `unit_price`, `time_left` |
| `bronze/items/YYYY-MM-DDTHHMMSS.parquet` | `dp items` run that fetched anything | `item`, `fetched_at`, `status`, `body` |

## The lake: DuckLake tables

One DuckLake catalog per environment: a SQLite file, `lake/catalog.sqlite`,
beside its Parquet data in `lake/data/`. DuckLake enforces no key, so a
table's key is the columns `dp` keeps unique by merging on them.

### `meta`

| Table | Key | Columns | Kept |
| --- | --- | --- | --- |
| `processed` | `market`, `hour` | `bronze_file`, `span`, `committed_at` | always |
| `gap` | `market`, `hour` | `found_at` | always |
| `migration` | `version` | `name`, `applied_at` | always |

`processed`'s latest hour is the high-water mark.

`migration` records the migrations applied, one row for each version. The
migrations are the files in `sql/migrations/`, applied in order by `dp
transform` before it reads anything, and the SQL of the hourly comparison is in
`sql/transform/`; the SQL of the daily close is in `sql/daily/`. All are embedded
in the binary.

### `silver`

Each hour replaces `live_listing` whole, since after the hour it holds exactly
the listings of that hour's snapshot. `event`'s `span` is never null: the first
hour collected writes no events.

| Table | Key | Columns | Kept |
| --- | --- | --- | --- |
| `live_listing` | `id` | `item`, `unit_price`, `quantity`, `time_left`, `first_seen`, `last_seen`, `posted`, `posting_lowest`, `posting_position`, `posting_units_ahead`, `posting_units_at_or_below` | while live |
| `listing_hour` | `id`, `hour` | `quantity`, `time_left`, `position`, `units_ahead`, `units_at_or_below` | while live |
| `event` | `hour`, `id`, `kind` | `item`, `units`, `unit_price`, `tier`, `rule`, `tie`, `span` | silver keep |
| `listing_record` | `id` | `item`, `unit_price`, `quantity`, `first_seen`, `last_seen`, `posted`, `duration`, `posting_lowest`, `posting_position`, `posting_units_ahead`, `posting_units_at_or_below`, `ended`, `outcome`, `outcome_tier`, `tie`, `units_sold`, `end_lowest`, `end_position`, `end_units_ahead`, `end_units_at_or_below`, `end_units_undercut` | silver keep |

### `gold`

Each hour's transform writes `price_level_hour` and `item_hour` in the hour's
one transaction, from the hour's live listings and events. `item_hour` has a
row for each item listed in the hour or in the hour held before it. `item_day`
is `dp daily`'s: its table is made with the others so that the views over it
work before the first day closes. A day is closed where `item_day` holds a row
of it. A day in which no item had a row has none, so `dp daily` closes it again
each night to no rows; and a day whose first hour is past the hourly keep is not
closed, since its hours are deleted.

| Table | Key | Columns | Kept |
| --- | --- | --- | --- |
| `price_level_hour` | `item`, `hour`, `unit_price` | `units`, `listings` | hourly keep |
| `item_hour` | `item`, `hour` | `lowest`, `units_listed`, `listings`, `posted_units`, `sold_floor_units`, `sold_estimate_units`, `expired_units`, `cancelled_units`, `span` | hourly keep |
| `item_day` | `item`, `day` | `lowest`, `median_fill_price`, `default_n`, `posted_units`, `sold_floor_units`, `sold_estimate_units`, `hours_held` | daily keep |

### `reference`

| Table | Key | Columns |
| --- | --- | --- |
| `item` | `item` | `name`, `class`, `subclass`, `vendor_sell_price`, `vendor_buy_price`, `fetched_at` |

`item` is rebuilt from bronze's item files: the latest response with status
200 for each item wins, by `fetched_at` and then by file name. A 404 is no
answer, so an item with only 404s has no row and one whose latest response is
a 404 after a 200 keeps the 200's. `name`, `class` and `subclass` are null
where the body lacks them; `vendor_sell_price` is 0 where it lacks
`sell_price`, and `vendor_buy_price` is null where it lacks `purchase_price` or
gives 0.

`dp transform` rebuilds it once in each run, after the hours, as its own
transaction, and writes nothing where the rebuilt table equals the one held.
The item files change only when `dp items` runs, before the transform in `dp
hourly`, so once a run is as current as once an hour; and a bad item file then
fails that step and not an hour.

## Views and macros

The measures of [5.2.3](5.2.3-consumable-profiles.md), defined once in
`sql/profiles.sql` over the gold and reference tables, named by schema as
`gold.item_hour` and `reference.item`, with no catalog. `dp` loads it over the
lake, as temporary views and macros; a client loads it from the export over
the export's files. The three windows are not written in it: it reads them
from the macros `default_n_window_hours()`, `turnover_window_hours()` and
`depth_ladder_cutoff_hours()`, which `dp` makes from its settings
([5.4.1](5.4.1-configuration.md#product-settings)), ahead of it.

| Name | Gives |
| --- | --- |
| `fill_price(item, hour, n)` | a struct of the average unit price of the cheapest *n* units in that hour, `price`, and the units it covers, `units`; null where none are listed; an error where *n* is below 1 |
| `default_n(item, hour)` | the default *N* ([5.2.3](5.2.3-consumable-profiles.md#the-price-now)), over the hours held in the window ending at the hour |
| `depth_ladder(item, hour)` | a table of each price level with its `units`, the units at or below it, and the `hours` they last, null for *no sales seen*, up to the cut-off |
| `profile` | for each item with a row at the latest hour: the reference columns (`name` is the ID until there is a response), `lowest`, `units_listed`, `default_n`, the fill price at it and the units it covers, and each flow's total over every hour held in the turnover window |
| `hourly_history` | each `item_hour` row, with the item's name |
| `daily_summary` | each `item_day` row, with the item's name |
| `held_hour` | the hours gold holds, with their span: a helper of the macros |
| `hour_number(hour)` | the hours since the epoch, the one place an hour becomes a number (no ICU) |

## The export

Written by `dp export`, plain Parquet that a client reads with only DuckDB and
rsync, each file under a temporary name and renamed into place; a client copies
only `*.parquet` and `profiles.sql`.

| File | Written |
| --- | --- |
| `export/price_level_hour/YYYY-MM-DDTHH.parquet`, `export/item_hour/YYYY-MM-DDTHH.parquet` | once for each committed hour within the hourly keep whose file the export lacks, oldest first; an hour with no rows has a file with the columns and no rows |
| `export/item_day.parquet`, `export/item.parquet` | rewritten where the table differs from the file |
| `export/profiles.sql` | views named as the gold and reference tables over the export's files, the settings macros, then `sql/profiles.sql` unchanged; rewritten where its text differs |

A committed hour's gold never changes, so a run with nothing new writes
nothing. An hour is within the hourly keep unless its start is more than the
keep before now, so the file of an hour exactly the keep ago stays; an hour
the export lacks and that is past the keep is not written. The hour in a file's
name is what `dp daily` measures its keep by. A run removes any `*.tmp` file a
killed run left, under the lock.

A client sets the variable `export_dir` to the export's folder before loading
`profiles.sql`; unset, the views read the working folder. Before the first hour
is exported the views have no files to read.

A copy of the export taken while `dp export` runs can hold a new hour's files
beside the previous `item_day`; the next copy brings them level.

## The bucket

Where the environment has a bucket, `dp daily` pushes to it:

| Object | Kept |
| --- | --- |
| `bronze/` and below, each bronze file under its host path | the bronze keep in the bucket |
| `daily/item_day.parquet`, `daily/item.parquet`, copies of the export's, rewritten | indefinitely |

`dp daily` puts the two `daily/` files every run, since they are rewritten, and
each bronze file once. What the bucket holds is what `dp` has recorded, one host
path to a line, in `state/bucket-pushed.txt`: a path is recorded once its push
has succeeded, so a push that fails is repeated by the next run. The mechanism
that puts a file there is provisional
([5.1.3](5.1.3-technology-decisions.md)) and reads nothing back.

## Expiry

`dp daily` deletes:

- lake rows past their keep time, then their files, by DuckLake's snapshot
  expiry and file clean-up: every night, whether or not a row was deleted, so a
  clean-up that failed is repeated, and the snapshots expired are all those
  before the run, which are the ones that still hold the deleted rows;
- bronze snapshot files on the host past the bronze keep on the host, once
  the bucket holds them where the environment pushes to one; item files are
  kept;
- export hour files past the hourly keep.

It also removes the `*.tmp` files a killed run left in bronze, except one a
running run may still be writing: a snapshot's, until the retry window of the
hour in its name has closed, and an item run's, until the hourly run after its
start has started.
